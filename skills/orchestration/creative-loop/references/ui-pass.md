# UI pass

Part of every review cycle, and run after any direction that adds or changes a menu, HUD, dialog or overlay. A player or visitor who meets cramped spacing or a wall of information at once will call the piece clunky however well it works. Under the game profile every step applies; under the others, step 3 uses the repo's own rules and the lab-only output in steps 1 and 2 is replaced as they say.

1. **Check output.** In the lab, `pnpm check <app>` prints `ui layout` lines for overlap, clipping, minimum font size, target size and gap, a words-per-screen budget, and the crowding rules: duplicate phrases, controls legend, choice groups per screen, words per tile, locked items and font-size count. Fix every `ui layout` FAIL at its cause, never by editing a threshold; fix a crowding failure by deleting or moving content, not by shrinking it. Alignment only informs: judge it on the screenshot. A screen near its words budget is a candidate for the next step. A repo whose check prints no such lines skips this step.
2. **Look at every screen.** Open `.verify/<app>/check/ui/screens.png` first (elsewhere, a contact sheet of the cycle's shots, for example with ImageMagick `montage`), every screen the check reached on one sheet, then each shot behind it (title, playing, pause, game over, settings, every overlay), and read them as a first-time player. The check reaches only the screens its bots pass through; open the others (a shop, a pick step, an overlay) yourself with `pnpm shot` or the app's URL parameters. Shoot each screen once more in its fullest state at the narrowest window the brief targets: stored records present (a best score, a rank, a streak), the longest value each field can hold, the device's fallback font. The check's bots see a fresh install, so a line that only appears after a first run is never in its shots. A line that wraps is rewritten as lines that each hold a whole phrase. Name what you see at once; if that is more than the screen's primary action plus the few things needed to take it, something is too early.
3. **Design rules.** Under the game profile, hold every screen to `game-design` `references/ui-ux.md` (play in two activations, one decision per screen, Back and focus, prompts, HUD in two tiers, pause and game over) and its words to `references/copy.md`; banners shown during play follow `references/play-field.md` rule 5. Each finding names its rule. Under the other profiles, hold every screen to the repo's own UI rules and the brief's look direction, and name the rule the same way.
4. **One spacing scale.** Pick a base step (for example 8 px) and use only its multiples for padding, gaps and margins; one scale for type sizes too. Controls get room to breathe and touch targets stay large enough with a gap between them.
5. **If `ui-polish` is installed**, run it on the DOM screens (menus, HUD, overlays) at desktop width, and at phone width only when the user asked for mobile (then also `pnpm check <app> --mobile`) or the brief names a phone width; it screenshots, checks the visual checklist and fixes styles. Its findings count as review findings. If it is missing, steps 1 to 4 stand alone.
6. **Remove one thing.** Name one element, option or screen that a player would not miss and remove it or move it behind a button. Nothing worth removing is a valid answer only when said with the screens checked.
7. **Log it.** A cycle that changes UI says so in its `## Cycles` line. A finding becomes a direction; a UI pass that finds nothing is part of a dry review, with the screens checked named in the entry.
